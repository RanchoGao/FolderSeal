# 发布流程

源码通过 Git 提交；安装包和便携包上传到 GitHub Release。Release 是与版本标签关联的下载页面。发布前先完成本地整理与核验，再确认提交范围。

## 产品命名

中文名为“密封夹”，英文名为“FolderSeal”；对外文档与 Release 标题使用“密封夹（FolderSeal）”。程序文件名、安装包名、仓库标识与数据路径沿用 FolderSeal。

宣传语为“你的文件，只有你能打开。”命名理由：不使用 AES-256 等技术术语，直接说明“未经授权打不开”的用户价值，并且容易记住。

## 目录与版本

- `src/` 保留一份最新源码，历史由 Git 保存。
- `assets/` 保存透明品牌 PNG 和多尺寸 ICO；修改底图后运行 `scripts/prepare-icon.ps1`，将生成的 ICO 随源码提交。ICO 使用真实 32 位色，同时保存 Alpha 与 AND 掩码；圆角外必须透明。构建脚本嵌入图标，并从安装定义生成程序版本信息。
- `tests/`、`scripts/`、`installer/`、`docs/` 与根目录说明文件随源码提交。
- `artifacts/` 只放本地构建与测试产物；`releases/<版本>/` 保存待发布或已发布附件，两者均不入库。
- `_personal/`、`_archive/`、`tools/` 为本地资料，不入库。`_archive/` 存放旧版本源码、程序与历史交付快照。

版本号从 `installer/FolderSeal.nsi` 的 `!define VERSION` 读取；CHANGELOG 记录变更、需求编号与验证范围。未发布时标记“待发布”，正式发布时填写实际日期。

## 本地验证与打包

在仓库根目录运行：

```powershell
.\scripts\build.ps1 -Validate -ValidateEntry -ValidateUi -ValidateIcon -ValidateInstance -ValidateLibrary -ValidateDiscovery -ValidateUpdate -ValidateShell
.\scripts\package.ps1
.\scripts\package-portable.ps1
```

两个打包脚本都会重新编译当前源码。期间不要修改源码和文档；不同次 .NET Framework 编译的程序哈希可能不同，需分别记录两份包内程序的 SHA-256 与对应源码的 SHA-256。

`-ValidateIcon` 检查 ICO 每个尺寸与 EXE 提取图标，背景预览输出到 `artifacts/test-work/icon-preview/backgrounds.png`。查看深色、白色和彩色背景上的边缘，确认没有白底、白边或残影。只查看原图或文件存在不能代替该项验收。

管理员 PowerShell 可另外运行：

```powershell
.\scripts\build.ps1 -ValidateAcl
.\scripts\verify-installer.ps1
```

安装验证脚本发现正式安装或同名开始菜单目录时会停止，以免影响已有软件。未执行或未通过的检查必须在发布说明中明确列出，不把编译成功写成安装验收通过。

将下面文件复制到 `releases/<版本>/`：

| 文件 | 用途 |
| --- | --- |
| `FolderSeal-<版本>-Setup.exe` | 完整安装包 |
| `FolderSeal-<版本>-Portable.zip` | 便携包 |
| `SHA256SUMS.txt` | 安装包校验值 |
| `PORTABLE-SHA256SUMS.txt` | 便携包校验值 |
| `发布说明.md` | Release 正文，含变化、升级方法与验证限制 |
| `构建记录.json` | 本地核验记录，保存源码与程序、软件包的哈希及检查结果 |

前四项作为下载附件。发布说明作为 Release 正文；构建记录默认仅在本地保存，分享前检查是否包含本机信息。替换已有本地发布附件前，将原附件保留到 `_archive/`，避免丢失交付快照。

## 提交与发布

程序从本仓库公开 Release 列表检测更新，包括已公开的预发布版本。要让已安装用户发现新安装包，必须公开 Release 并上传完整的 `FolderSeal-<版本>-Setup.exe`，标签使用 `v<版本>`。仅提交代码、打标签或生成本地包不会触发升级提示；预发布状态会在下载确认中标明。发布包不要在尚未通过必要检查时改为正式版。

先检查 `git status --short`、`git diff --check` 及完整差异，确认没有私人资料、密文、凭据、工具和二进制产物进入提交。对外署名使用 EurekaGao。

提交信息采用“类型: 具体变化（需求编号）”，例如 `feat: 优化主界面与锁定状态提示（R-008）`。一次提交围绕同一个目的，发布整理可使用 `chore` 或 `docs`。

提交前向维护者展示变更文件、验证结果、拟用提交信息和 Release 附件清单。维护者确认后再执行提交、推送、创建 `v<版本>` 标签及 GitHub Release；标签必须指向包含本次代码与文档的提交。若管理员验收尚未完成，Release 标记为预发布（Pre-release，表示仍有验证工作未完成）。

最后核对远端分支和标签实际指向的提交，并核对上传附件的名称、大小与 SHA-256；本地文件存在不等于远端发布成功。

## GitHub Actions 自动构建与发布（推荐）

仓库已配置两条公开工作流（GitHub 托管的 `windows-latest` 环境）：

- **`.github/workflows/ci.yml`**：每次推送或 PR 到 `main` 时自动运行 `.\scripts\build.ps1 -ValidateAll -ValidateAcl`，公开展示构建与权限验证状态。
- **`.github/workflows/release.yml`**：推送 `v<版本>` 标签（须与 `installer/FolderSeal.nsi` 中的 `!define VERSION` 一致）后自动触发：
  1. 校验标签版本号与 `FolderSeal.nsi` 一致；
  2. 运行全量验证（含管理员 `-ValidateAcl`）；
  3. 通过 `-SkipBuild` 复用同一份 `FolderSeal.exe` 生成便携包、安装包与 `SHA256SUMS.txt` / `PORTABLE-SHA256SUMS.txt`；
  4. 为双包生成 **SLSA Build Provenance Attestations**（可用 `gh attestation verify` 校验）；
  5. 创建 **Draft Release**（草稿状态，防止误推标签直接触发已安装用户的应用内更新），由维护者在 GitHub 页面核对后手动点击发布。

也可在 GitHub Actions 页面手动运行 `Release` 工作流（留空 `tag` 参数）进行演练构建，不创建 Release。

### 启用 SignPath Foundation 双阶段代码签名（可选，获批后操作）

若后续向 [SignPath Foundation](https://signpath.org/apply.html) 申请免费开源代码签名获批，无需重写工作流，仅需 3 步即可启用双阶段签名（先签 `FolderSeal.exe`，再打包，再签 `Setup.exe` 并重算 `SHA256SUMS.txt`）：

1. 在 GitHub 仓库安装官方 SignPath GitHub App，并在 SignPath 后台绑定 `.github/workflows/release.yml` 为 Trusted Build System，配置 `folderseal-exe` 与 `folderseal-setup` 两项产物配置及手动审批策略（`release-signing`）；
2. 在 GitHub 仓库 `Settings → Secrets and variables → Actions` 配置 Secrets：`SIGNPATH_API_TOKEN`、`SIGNPATH_ORG_ID`，以及 Repository Variable：`SIGNPATH_ENABLED=true`；
3. 同步更新根目录 [CODE_SIGNING.md](../CODE_SIGNING.md) 中的当前状态与归属声明。

单实例回归使用随机命名管道与生成的样例目录，验证不同副本转交、快速重复启动、无效消息拒绝及退出/崩溃后重启。升级验收需先关闭所有旧版窗口，再检查新版本重复启动及资料入口转交。
